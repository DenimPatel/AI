LLM Training, Interactively

Every chat assistant you've used — Claude, GPT, Gemini, Llama — went through the same broad pipeline: a base model learns language by predicting text, then it's shaped into an assistant, then it's aligned to be helpful and safe. Most labs won't show you the middle of that pipeline. This guide will, using OLMo, the model family from the Allen Institute for AI (Ai2) that publishes its dataset, its code, and hundreds of checkpoints from an actual training run — so every claim here points at something you can go inspect yourself.

Why OLMo, and what this series covers

Setup

Most "open" models today are really only open-weight: you get the final numbers, not how they got there. The exact web-crawl recipe, the filtering thresholds, the preference data, the reward model — those stay inside the lab. That's a problem if you actually want to understand training, not just call an API.

OLMo (Ai2) is built differently. Ai2 releases the pretraining corpus (Dolma, a multi-trillion-token corpus, along with the exact curation code), checkpoints saved roughly every 1,000 training steps, full loss curves and hardware logs, and a tool called OlmoTrace that lets you trace a specific generated response back to the pretraining documents that most likely shaped it. We'll lean on OLMo throughout this series as the concrete, verifiable example behind each abstract idea.

💡 The shape of the series: Part 1 (this page) covers what a language model even is — tokens, embeddings, next-token prediction. Part 2 covers the pretraining dataset. Part 3 covers pretraining itself — the training loop that turns data into a base model. Part 4 covers supervised fine-tuning, which turns a base model into something that follows instructions. Part 5 covers alignment — RLHF and DPO. Part 6 covers guardrails — safety, evaluation, and deployment.

Prerequisites: comfort with vectors, matrices, probability, and basic calculus — the level of a first-year graduate course. We'll define every model-specific term as it comes up.

1

A language model is a probability distribution over the next word

Foundations

Strip away the transformer architecture, the GPUs, the trillions of tokens, and a language model is answering one narrow question, over and over: given the text so far, what word (or token) is likely to come next? Formally, it defines a conditional probability distribution

P(xₜ | x₁, x₂, …, xₜ₋₁)

over its vocabulary, where xₜ is the next token and x₁…xₜ₋₁ is everything said before it. Chain that one-step prediction together — predict a token, append it, predict the next one — and you get a model that can generate whole passages. This is called autoregressive generation, and it's the objective every GPT-style model, including OLMo, is pretrained on.

🎯 Learning goal: a language model doesn't "know" the next word — it estimates how likely each candidate is, given everything it's seen. A bigram model estimates this from one previous word; OLMo estimates it from up to thousands of previous tokens, using a transformer instead of a counting table — but the object being predicted is exactly the same shape.
2

Before prediction: turning text into tokens

Foundations

Models don't operate on characters or whole words directly — they operate on tokens, chunks of text drawn from a fixed vocabulary (OLMo 2 uses a vocabulary of roughly 100K tokens). The dominant scheme is byte-pair encoding (BPE): start with individual characters, then repeatedly merge the most frequent adjacent pair into a single new token, building up from characters to common subwords to common whole words. Frequent words like the end up as one token; rare or unfamiliar words get split into several subword pieces.

Start: "the" → t, h, e
Merge frequent pair (t, h) → "th"
Merge frequent pair (th, e) → "the"
Repeat for thousands of merges, most-frequent pair first, until the vocabulary is full

Below is a small illustrative BPE tokenizer — trained on the same toy passage, with far fewer merges than a real one — so you can see the mechanism, not a production vocabulary. Type anything and watch it split.

⚠️ Watch for: type a word that never appeared in the toy passage (try tokenization itself) and it falls back to individual characters — there's no merge rule for it. A real tokenizer trained on trillions of tokens rarely falls back this far, but the same principle holds: unfamiliar strings cost more tokens, which is part of why token counts (and API pricing) vary by language and domain.
3

Tokens become vectors

Foundations

Once text is tokens, each token ID is looked up in an embedding table — a big matrix, one learned row-vector per vocabulary entry — turning a sequence of integers into a sequence of vectors in, say, ℝ4096 (OLMo 2 32B uses a 5,120-dimensional hidden size). These vectors start out essentially random and are updated by training just like every other weight in the model. What makes them useful is that training pulls tokens used in similar contexts toward similar vectors — not because anyone hand-labels "cat is similar to dog," but because predicting the next token correctly requires it.

4

Putting it together: autoregressive generation

Foundations

Tokenize the prompt, look up embeddings, run them through the network to get a probability distribution over the next token, pick one (more on how to pick in Part 3), append it, and repeat. That loop — one forward pass per new token — is exactly how every response you've ever gotten from a chat model was produced. Use the same bigram model from Step 1 to generate a few tokens yourself:

⚠️ Notice: a bigram model only remembers one word back, so it wanders and repeats quickly. Real transformer models condition on the entire preceding context (OLMo 2 supports contexts of several thousand tokens), which is most of why they stay coherent — not a fundamentally different objective, just vastly more context and a vastly better function approximator (the transformer) doing the predicting.
