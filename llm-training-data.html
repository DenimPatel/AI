Building the pretraining dataset

A base model is, in a real sense, a compressed summary of the text it was trained on — so what goes into that text matters enormously, and gathering it is its own multi-stage engineering problem, well before any GPU runs a training step. We'll follow Dolma, Ai2's fully open pretraining corpus for OLMo, through the pipeline that turns raw web crawls into training-ready text.

{% raw %}
1

Where the text comes from

Sourcing

No single source has enough high-quality text at trillion-token scale, so pretraining corpora blend several. Dolma mixes web crawl text (via Common Crawl) with more curated sources: code repositories, academic papers, encyclopedic text, and public-domain books. Each source contributes differently — web text gives breadth and volume, code gives structured reasoning patterns, papers and encyclopedic text give density of factual, well-edited prose.

💡 Why this matters: the mixture is itself a hyperparameter. Overweight web text and you get breadth but noise; overweight code and math ability improves but general fluency can suffer. Ai2 publishes not just the sources but the exact mixing ratios used for each Dolma release, so this trade-off is something you can actually inspect rather than guess at.
2

The filtering funnel

Cleaning

Raw Common Crawl is mostly not useful training text — boilerplate, navigation menus, spam, non-English pages, near-duplicate pages mirrored across sites. Dolma's pipeline (released as open-source code, not just a description) runs each document through a sequence of filters, each one discarding a further slice:

raw crawl → language filter → quality filter → deduplication → PII / toxic-content removal → training-ready text

Step through the pipeline below. Percentages are illustrative — a representative shape for a web-crawl cleaning pipeline, not exact published Dolma figures — but the ordering and the scale of the drop is realistic: most of the discarding happens in language and quality filtering, long before dedup ever runs.

⚠️ Quality filtering is the trickiest stage: Dolma uses a mix of heuristic rules (too short, too repetitive, too many symbols relative to words) and trained classifiers (does this page resemble the kind of text people actually found useful, e.g. Wikipedia-referenced pages) to score documents. Get the threshold wrong and you either keep boilerplate or throw away legitimate but unusual text — there's no ground truth to check against.
3

Deduplication: finding near-identical documents

Cleaning

The web republishes the same content constantly — syndicated news, mirrored docs, boilerplate templates. Training on many near-duplicate copies wastes compute and can make the model memorize that specific text more than is useful. Exact-duplicate removal (hashing whole documents) catches identical copies; Dolma also runs fuzzy deduplication using MinHash, which estimates document similarity without comparing every pair of documents directly (infeasible at trillions of tokens).

The core similarity measure is Jaccard similarity between two documents' sets of overlapping word "shingles" (short n-grams):

J(A, B) = |A ∩ B| / |A ∪ B|

Decontamination: keeping the exam out of the textbook

Cleaning

If a benchmark's evaluation questions (or worse, its answers) leak into pretraining data, the model can score well by memorization rather than by genuine capability — inflating reported results. Dolma's pipeline explicitly screens for and removes text that overlaps with known evaluation sets, a step usually called decontamination. This is another place where transparency matters: if you can't see the training data, you can't verify that a benchmark score means what it claims to mean.

💡 PII and safety scrubbing happen around the same stage: filters look for patterns resembling personal data (emails, phone numbers, ID numbers) and remove or mask them, and classifiers flag clearly toxic or unsafe pages for removal — separate from (and a preview of) the more targeted safety work in Part 6.
5

Data mixing, and other fully-open recipes

Wrap-up

The final step isn't just "keep what survives filtering" — it's choosing how much of each surviving source to actually show the model, and in what order across training (some recipes upweight higher-quality sources late in training). Getting this mixture right is empirical: labs train smaller models on candidate mixtures and measure downstream performance before committing a mixture to a full-scale run.

If you want to go deeper on this stage specifically, two other fully-documented efforts are worth reading: Hugging Face's FineWeb, which publishes both a massive filtered web dataset and a very detailed write-up of exactly which filtering choices moved benchmark scores, and Pythia (EleutherAI), an older but foundational suite built specifically to make data and training dynamics inspectable for research.
