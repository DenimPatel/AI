Guardrails, evaluation, and shipping the model

Alignment in Part 5 shapes the model's own behavior through training. This final stage adds the layer on top: explicit safety training, adversarial testing, evaluation against both capability and harm, and runtime guardrails — the difference between a model that behaves well in a lab and a system that holds up once millions of people, some of them deliberately trying to break it, start using it.

{% raw %}
1

Safety fine-tuning and the over-refusal trade-off

Training-time safety

Some safety work happens the same way as Parts 4 and 5: more (prompt, response) and preference examples, this time specifically targeting harmful, dangerous, or disallowed requests, teaching the model to refuse or redirect. Approaches like Constitutional AI go further, having the model critique and revise its own responses against a written set of principles, then training on the revised versions — reducing reliance on humans manually writing every refusal example.

The hard part is the threshold: too permissive and genuinely harmful requests get answered; too strict and the model starts refusing harmless requests that merely resemble harmful ones (a chemistry student asking about a reaction mechanism; a novelist asking about how a robbery might be planned for a story). 2

Red-teaming: testing it like an adversary would

Adversarial evaluation

Red-teaming means deliberately trying to make the model fail — jailbreak prompts, role-play framings designed to bypass refusal training, instructions hidden inside seemingly unrelated text — done by dedicated internal teams, external researchers, and increasingly other models trained specifically to generate adversarial prompts. Findings feed back into more safety training and, sometimes, runtime guardrails, since not every failure mode can be fully trained away.

⚠️ This demo is deliberately shallow — a few hardcoded phrase patterns, not a real safety classifier — to illustrate the idea of a guard layer. Real guardrail systems use trained classifiers, not keyword matching, precisely because keyword matching is trivial to evade (as you can check yourself: try rephrasing the same request without the flagged words).
3

Evaluation: benchmarks as a check, not a target

Measuring what happened

Before and after each training stage, models are run against benchmark suites (general knowledge, reasoning, coding, safety-specific evals) and, increasingly, human evaluation for qualities harder to automate — helpfulness, tone, honesty about uncertainty. The site's own benchmarks page tracks how several of these evals have moved across the field over time.

💡 Goodhart's law applies directly here: "when a measure becomes a target, it ceases to be a good measure." If a lab optimizes hard against a specific public benchmark (including, in the worst case, training on data that overlaps with it — the decontamination problem from Part 2), the benchmark score can rise without real capability rising with it. Cross-checking against held-out, less-gameable evals (and, per Part 3, being able to inspect training data directly) is the main defense.
4

Deployment-time guardrails

After training ends

Training produces the model's weights, but a deployed product usually wraps those weights in additional layers that can be updated far faster than retraining: a system prompt setting context and constraints for every conversation, and separate lightweight classifier models screening inputs before they reach the main model and outputs before they reach the user.

user input→ input guard classifier→ system prompt + trained model→ output guard classifier→ response shown to user

This layered approach exists because training-time alignment and deployment-time guardrails fail differently: a training gap requires another training run to fix, while a classifier or system-prompt gap can often be patched within hours of discovery — the two are complementary, not substitutes for each other.

Every phase reuses the same underlying machinery — tokens, embeddings, a next-token-shaped loss, gradient-based updates — applied to progressively narrower, more curated, more human-judgment-laden data. That's the throughline of this whole series: the leap from "predicts text" to "usable assistant" isn't one algorithm, it's this sequence of training stages, each fixing a specific gap the previous one left open.
