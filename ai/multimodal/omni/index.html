Omni models and the real-time loop

The last step is to put every modality into one model and run it live. That means text tokens and audio tokens in a single interleaved stream, an input stream and an output stream open at the same time, and a reply that begins while the user is still able to interrupt it. None of that is a modelling flourish: full duplex turns the whole problem into a latency budget, where every stage — recognition, network, the first text token, the first audio token — spends from the few hundred milliseconds a listener will tolerate. This part assembles the loop and does the accounting.

1

One model, many streams

Interleaved tokens in one sequence

An omni model does not concatenate modalities at the edges; it interleaves them, so a single sequence alternates text subwords, image patches and codec audio tokens in whatever order the task requires. The training objective is unchanged — predict the next token — but the vocabulary is shared and the model has to learn when a text token should follow an audio token and when it should not. That single sequence is what lets a model answer a question about a recording, quote a phrase it just heard, or switch from describing a picture to reading a caption aloud, without a routing layer deciding which sub-model to call.

The cost is a shared budget again, this time for output as well as input: audio tokens are far more numerous per second than text, so a stream that talks spends its context on sound. The thinker and the talker

Text for reasoning, audio for delivery

One way to keep the quality of a language model while producing speech natively is to split the decoding into two stages that share the same trunk. A thinker decodes text tokens as an ordinary language model, which is where the reasoning, the factual grounding and the instruction following live. A talker takes the thinker's hidden states — not just its sampled tokens — and emits audio codec tokens for the reply. The talker is small relative to the thinker, and because it conditions on hidden states rather than on finished text, it can start before the sentence is complete.

The split buys three things. Text stays inspectable and controllable, since you can read what the model "meant" to say. The audio rate can be chosen independently of the text rate, so the talker can stream in whatever codec the deployment uses. And the two can overlap: the thinker writes ahead while the talker catches up, which shortens the time to the first audible syllable — the number the user actually feels.

The thinker-and-talker split: audio tokens in, a text decoder that reasons, and a small audio decoder reading the thinker's hidden states to emit speech tokens in parallel.

A single-model alternative exists: one transformer emitting text and audio tokens in one sequence, as Moshi does with parallel user and model streams. The split is a practical compromise that keeps a strong text backbone intact.

⚠ Streaming audio decode is not free. The talker emits hundreds of codec tokens per second of speech, which is a token rate no text model ever faces. Splitting the decoders keeps that load out of the reasoning path, but it is still compute — and on one GPU it competes with the thinker for the same silicon.
3

Speaking while listening

Full duplex and the interrupt

A turn-based system alternates: listen, decode, answer. A full-duplex model keeps both streams open, so it can be listening for a new utterance while it is still producing the current reply. That is what makes barge-in work. When the user starts talking mid-reply, the model must not merely stop — it must keep the audio it heard, revise its plan and respond to the interruption. A turn-based pipeline handles this poorly, because the interrupt arrives while its synthesis stage is mid-sentence and its recogniser has not been running.

The timeline below models one turn: the user's speech, recognition overlapping its end, the reply gap assembled from the network hop, the time to first text token and the time to first audio token, and the assistant's reply. Flip the barge-in switch and a reply that has not started yet is cancelled, which is the cheap case; a reply already in flight is the expensive one.

One turn from GenMedia.timeline.turn, with the reply gap's stages assembled by GenMedia.timeline.budget. The barge-in marker cancels a reply that has not yet begun.

💡 Full duplex is a policy, not just a speed. Keeping the input stream open while speaking means the model can be interrupted gracefully, and it also means the model can be trained on overlapping speech — the back-channels, the "mm-hm", the false starts — that a turn-based interface throws away.
4

The realtime budget

Everything on one GPU

The latency a listener feels is not the sum of the pipeline's work; it is the gap between the end of their speech and the first sound of the reply. Streaming recognition overlaps the speech, so it does not sit in that gap, but the network hop, the time to the first text token and the time to the first audio token all do, and together they have to fit inside roughly 200–300 ms. Under load that arithmetic breaks, because the audio decoders, the recogniser and the thinker share one accelerator: every extra concurrent conversation multiplies the work on the same silicon.

The budget bar below sums the stages and scales the compute-bound ones by the load slider, so you can watch a comfortable budget cross the 300 ms line without any single stage becoming unreasonable. That crossing is the reason serving a real-time voice model is a scheduling problem as much as a modelling one.

The reply budget from GenMedia.timeline.budget, drawn with Guide.drawStacked. The dashed line is the 300 ms target; the load slider scales every compute-bound stage together.

⚠ Average latency hides the tail. A model can average 250 ms and still feel broken if one reply in twenty takes 900 ms, so the budget is set against a percentile, not a mean. Batching several conversations together improves throughput and worsens exactly the tail the voice interface is judged on.

Where this shows up

The loop, closed

Speech in, speech out

One model, no cascade

Moshi models the user's audio and its own audio as parallel streams in one transformer and drops explicit speaker turns; Qwen2.5-Omni pairs a thinker writing text with a talker emitting speech tokens. Both are the architecture this part has been assembling, and both are described in more detail alongside the recognition machinery in the audio volume.

Serving

Realtime voice as a workload

A duplex conversation is a serving problem before it is a modelling one: long-lived streaming requests, very small batches, a hard tail-latency objective and a prefix cache that turns over every turn. The workload treatment of realtime voice, with the same budget numbers, is LLM Serving, workloads.

That closes the arc. It began with cutting an image into patches and ends with one trunk reading text, images, video and audio in a single interleaved sequence while a conversation runs at the speed of speech. The pieces in between — the shared space, the bridge, resolution, hallucination, video's token arithmetic, audio's two front ends — are all in service of this loop.

Further reading

The omni literature is young and moves fast. These papers cover the two-stream speech-text model, the thinker-talker split, and the first attempts to put speech into a language model's own token space.

  • Alexandre Défossez, Laurent Mazaré, Manu Orsini and coauthors, "Moshi: a speech-text foundation model for real-time dialogue", 2024 — full-duplex speech-to-speech with parallel user and model streams in one transformer.
  • Jin Xu, Zhifang Guo, Jinzheng He and coauthors, "Qwen2.5-Omni Technical Report", 2025 — a thinker writing text and a talker emitting speech tokens, stream-decoded for low first-package latency.
  • Dong Zhang, Shimin Li, Xin Zhang and coauthors, "SpeechGPT: Empowering Large Language Models with Intrinsic Cross-Modal Conversational Abilities", 2023 — discrete speech units placed in a language model's token space.
  • Paul K. Rubenstein, Chulayuth Asawaroengchai, Duc Dung Nguyen and coauthors, "AudioPaLM: A Large Language Model That Can Speak and Listen", 2023 — one model over joint text and audio token vocabularies.
  • Qingkai Fang, Shoutao Guo, Yan Zhou and coauthors, "LLaMA-Omni: Seamless Speech Interaction with Large Language Models", 2024 — the thinker-talker decomposition for low-latency spoken replies.
