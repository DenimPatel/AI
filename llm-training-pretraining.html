Pretraining at scale

With a cleaned, trillion-token dataset from Part 2, pretraining is the process that turns it into a base model: a transformer network is shown token sequences over and over, scored on how well it predicts the next token, and nudged to do slightly better each time — repeated for hundreds of thousands of steps across thousands of GPUs. We'll build the training loop up piece by piece, checking each piece against what Ai2 actually published for OLMo.

{% raw %}
1

Self-attention: letting tokens look at each other

Architecture, briefly

A transformer block's key operation is self-attention: for every token, decide how much to "look at" every other token before it, and blend their information accordingly. Each token's embedding is projected into a query, key, and value vector; a token's query is compared against every other token's key to get attention weights, which then weight a sum of value vectors:

Attention(Q, K, V) = softmax( QKᵀ / √dₖ ) V

This is the mechanism that lets "it" in a sentence attend back to the noun it refers to, or lets a verb attend to its subject several words earlier — all learned, not hand-coded. Below is a toy (not a trained model's real) attention pattern for one short sentence, built from hand-placed word similarity so you can see the shape of the computation: each row sums to 1, and shows how much that word's new representation depends on every other word.

Darker cell = higher attention weight from the row word to the column word. This is illustrative, not extracted from a real trained model.

🎯 Learning goal: attention is what lets a transformer condition on the whole context at once (unlike our Part 1 bigram model, which only saw one word back) — and stacking many attention layers lets the model build increasingly abstract representations of the text so far, layer by layer.

A full derivation of multi-head attention and the rest of the transformer block (feed-forward layers, residual connections, layer normalization) is beyond an interactive intro page — see "Attention Is All You Need" in Further Reading for the complete architecture.

2

The training loop: loss, backprop, update

Foundations

Each training step: take a batch of token sequences, run the forward pass to get a predicted next-token distribution at every position, compare it against the actual next token using cross-entropy loss, then use backpropagation to compute how every one of the model's (often tens of billions of) parameters should change to reduce that loss, and apply an update via an optimizer — almost always AdamW for language models, an adaptive variant of gradient descent with weight decay.

L = − (1/T) ∑ₜ log Pθ(xₜ | x<ₜ)   (average negative log-likelihood of the true next token, over all T positions in the batch)

Notice this is exactly the objective from Part 1's bigram model, generalized: instead of counting frequencies in a table, a transformer's parameters θ are adjusted by gradient descent so that Pθ assigns higher probability to the tokens that actually followed, across trillions of examples.

⚠️ Scale is the whole story here: OLMo 2 32B was trained on roughly 6 trillion tokens. There is no shortcut around running this loop an enormous number of times — which is precisely why the dataset quality from Part 2, and the training efficiency choices in this part, compound into such large differences in the final model.
3

The learning-rate schedule

Training dynamics

The optimizer's step size — the learning rate — isn't fixed through training. The standard recipe (used across OLMo and most modern LLMs) is linear warmup followed by cosine decay: start near zero, ramp up over the first ~1–2% of steps (starting at full learning rate on randomly-initialized weights is unstable and can diverge), hold near a peak, then decay smoothly toward a small final value as training ends.

💡 Too little warmup and early training can blow up (huge gradients on an untrained model); too high a peak learning rate and loss oscillates or diverges later; decaying too early wastes the compute budget on preventable under-training. Published training reports like OLMo's include the exact schedule used, which is part of what makes a run reproducible rather than folklore.
4

From distribution to text: sampling and temperature

Inference

Training produces a model that outputs logits (unnormalized scores) for every vocabulary token. Turning that into an actual next token requires a decision rule. Always picking the highest-probability token (greedy decoding) is deterministic but often dull and repetitive; sampling introduces controlled randomness. Temperature reshapes the distribution before sampling:

P(xₜ) = softmax(logits / T)   T < 1 sharpens the distribution, T > 1 flattens it, T → 0 approaches greedy decoding

⚠️ Trade-off: low temperature is safe and repetitive; high temperature is more diverse but risks incoherence. Production chat systems typically also use top-p (nucleus) sampling alongside temperature, restricting sampling to the smallest set of tokens whose cumulative probability exceeds p — not shown here, but the same softmax-reshaping idea underneath.

Watching it happen: loss curves and checkpoints

Evidence, not folklore

Most labs report a final loss number, if that. Ai2 published OLMo's entire loss curve, along with model checkpoints saved roughly every 1,000 training steps — so instead of taking "capability emerges gradually" on faith, you can download a checkpoint from any point in training and test it yourself. 💡 OlmoTrace takes this a step further at inference time: given a specific generated response, it searches back through the training corpus for documents whose text plausibly shaped that output — turning "the model said X" into "the model said X, and here's training text that looks like why," which is a genuinely different level of auditability from a closed model.
